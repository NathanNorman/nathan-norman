Four Hooks Patterns for
Steering Claude Code

A rule in CLAUDE.md is guidance that Claude can skip. A hook is code that runs on every matching tool call. These are the four hook patterns my Claude Code setup is built on, with tested code and the way each one fails.

Claude Code loads CLAUDE.md into every session as context, and Claude decides how to apply it. The memory docs describe the file as a user message that follows the system prompt. Claude tries to follow it, and nothing guarantees strict compliance. Length makes it worse: the docs recommend keeping the file under 200 lines because longer files reduce adherence.

The file stays in context for the whole session, since Claude Code re-reads the project-root CLAUDE.md from disk after it compacts a long conversation. Staying in context is different from being followed. For a rule that has to hold every time, the same docs point to hooks.

A hook is a handler, usually a shell script, that Claude Code runs at a fixed point: before a tool call, after one, or when a session starts or ends. A PreToolUse hook sees the tool call Claude has built, as JSON, before the call runs. It can block the call and tell Claude why, and it runs in every permission mode, including bypassPermissions, the mode that skips permission prompts.

My setup has 19 hook handlers in ~/.claude/settings.json. One of them, an orchestrator for Bash commands, runs 12 check scripts. The four patterns below are the ones that setup rests on. Three of them have failed me in practice, and every failure I traced was in my own code, never in Claude Code’s hook machinery. A hook repeats its mistake on every matching call without raising an error, so each pattern ends with the way it fails.

Pattern 1: Block a tool call before it runs

When: a tool call should be blocked or redirected before it runs.

A PreToolUse hook is registered under a matcher, such as Bash, that picks which tool’s calls it sees. Claude Code writes each call to the script’s standard input as JSON, with fields including session_id, cwd, tool_name, and tool_input. For Bash, tool_input holds the command. The script answers with its exit code:

  • Exit 2 blocks the call. Claude reads whatever the script wrote to stderr as the reason, so it can change course.
  • Exit 0 means no objection. The normal permission check still runs.
  • Any other code, including 1, is a non-blocking error, and the call goes through.
#!/bin/bash
# PreToolUse hook on Bash: block find rooted at / or the home directory.
cmd=$(jq -r '.tool_input.command // ""')

# find, then /, ~, ~/, or $HOME, then a space or the end of the command
if grep -qE '(^|[;&|[:space:]])find[[:space:]]+(/|~/?|"?\$HOME/?"?)([[:space:]]|$)' <<<"$cmd"; then
  echo "Blocked: find on / or ~ walks the whole disk. Use the Glob or Grep tool." >&2
  exit 2   # block the call; Claude reads stderr as the reason
fi
exit 0     # no objection; the normal permission check still applies

The if field keeps the script from starting for commands that can’t match. It takes permission-rule syntax, and Claude Code checks it against every subcommand, so ls && find / -name x still triggers the hook:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(find *)",
            "command": "$HOME/.claude/hooks/checks/block-broad-find.sh"
          }
        ]
      }
    ]
  }
}

Exit 2 is the short form. A hook can instead exit 0 and print JSON that sets permissionDecision to deny, ask, or allow. With ask, the user gets a confirmation prompt instead of Claude getting a refusal, which suits commands that are sometimes right.

How it fails: a pattern sees text, not intent

A regular expression over a command string fails in both directions. Before I tested them against the commands they targeted, five of my checks did the opposite of their job:

Command What the check did What it should do
find ~/ -name '*.log' Allowed Block
find ~/src -name x Blocked, because the pattern matched every path starting with / or ~ Allow
git rm old.txt Blocked Allow
rm -rf . Allowed Warn
git push --force-with-lease Blocked, by a check whose own message recommends that flag Allow

My setup produced two more examples. My rm check once blocked a read-only test script because quoted test data in it contained rm -rf. My push-to-main check ran git in the hook’s working directory, which is the session’s directory, not the one the command was about to cd into. When I pushed a private repository from a session that had started in my public site repository, the check blocked the push and named the site repository.

Permission rules share this limit. The permissions docs say a Bash rule matches the form of a command Claude usually writes and is not a security boundary around the program. A regex in a hook is no different: cd / && find . walks the same disk as find /. For enforcement that doesn’t depend on command text, the docs point to the sandbox. I treat PreToolUse checks as guardrails against Claude’s habits, and I pipe test commands through each one, including commands it should allow:

echo '{"tool_input":{"command":"git push --force-with-lease"}}' \
  | ~/.claude/hooks/checks/prevent-force-push.sh; echo "exit $?"

Pattern 2: Run every check through one orchestrator

When: several checks inspect the same event.

Registering each check as its own hook works until the checks interact. Claude Code runs every matching hook in parallel and lets each one finish, even after another has denied the call, so one check’s block doesn’t stop another check’s side effects. Some checks rewrite a command instead of blocking it, by printing JSON with an updatedInput field. When two hooks rewrite the same call, the hooks guide says the last one to finish wins, and the order isn’t fixed.

An orchestrator is a single registered hook that runs the checks itself, in a fixed order, and stops at the first block. Each check reads the same JSON a hook would, so it also works as a standalone hook or from a test pipe:

#!/bin/bash
# PreToolUse hook on Bash: send the same input to each check, in order.
# A check exits 2 to block (its stderr is Claude's reason) or 0 to pass.
input=$(cat)
checks="$HOME/.claude/hooks/checks"

# Blocks first, rewrites last: a check that prints JSON ends the run.
for check in block-broad-find.sh prevent-force-push.sh rm-warn-once.sh; do
  out=$("$checks/$check" <<<"$input")
  status=$?
  [ "$status" -eq 2 ] && exit 2
  if [ "$status" -ne 0 ]; then       # missing or crashed: fail closed, loudly
    echo "Hook check $check failed with exit $status. Fix it before running commands." >&2
    exit 2
  fi
  [ -n "$out" ] && { echo "$out"; exit 0; }
done
exit 0

Three rules come with the loop. Blocks run before rewrites, because a check that prints JSON ends the run. A check that is missing or crashes blocks the command with a message instead of passing silently. A rewrite returns the whole tool input, because updatedInput replaces the input object and drops any field left out.

How it fails: a rewrite in the wrong place

My orchestrator has ten checks that block and two steps that rewrite. One rewrite appends || true to pytest and ruff runs, so a failing test doesn’t stop Claude partway through a fix. A comment said that step had to run last. I later added two checks below it, one of them the check that blocks git commit and git push in a single command.

After that change, git commit -am wip && git push was blocked, but pytest -q && git commit -am wip && git push was rewritten, approved with permissionDecision: "allow", and never reached the check. The appended || true also covered the push, so a failed push would have reported success. And the rewrite returned only the command, which dropped the call’s timeout and background flag.

That orchestrator was 179 lines of repeated if blocks, with the ordering rule in one comment among them. In the loop above, the whole order is one line, and a check in the wrong position is easy to spot.

Pattern 3: Warn once per session

When: a check should warn once per session and then step aside.

Some commands deserve friction the first time and not after. A warn-once check blocks the first rm of a session with a short checklist and lets later ones through. To do that it needs to know which session it is in, and every hook already receives session_id as one of its input fields.

#!/bin/bash
# PreToolUse check: block the first rm in a session with a warning; let later ones run.
input=$(cat)
cmd=$(jq -r '.tool_input.command // ""' <<<"$input")
session=$(jq -r '.session_id // "unknown"' <<<"$input")

# rm at the start of a command or after ; & |, so "git rm" passes
grep -qE '(^|[;&|])[[:space:]]*rm[[:space:]]' <<<"$cmd" || exit 0

state="$HOME/.claude/hooks/state/rm-warned/$session"
[ -f "$state" ] && exit 0            # already warned in this session
mkdir -p "$(dirname "$state")" && touch "$state"
echo "First rm this session. List what it deletes and confirm with the user, then run it again." >&2
exit 2

The state directory holds one empty file per session. A SessionEnd hook can delete a session’s files when it closes, and SessionEnd hooks get a 1.5-second default budget, which is enough for rm. Hooks declared in a skill’s frontmatter can set once: true to remove themselves after their first successful run, but a block doesn’t count as success, and settings files ignore the field.

How it fails: keying state on a process

My checks used to identify the session by walking up the process tree to the claude process and using its process ID. The walk is fragile. On macOS, ps -o comm= prints the binary’s full path, so comparing the name with claude never matches, and a version that falls back to its parent’s process ID gets a new ID on every tool call when an orchestrator launches it. In a test harness, that version produced three different session IDs for three calls and warned every time.

Mine compared the basename, so it found the right process. A process ID still identifies a process, not a conversation. One of my desktop-app conversations ran on three different Claude Code processes in under a day, the last one after a version update, and my push warning fired once in each. The session ID stayed the same throughout.

Stale files piled up too. My state directories held files from May, because cleanup removed a file only when its process had died and that particular check happened to run, and process IDs get reused. Four of my other hooks already read session_id from their input; these checks hadn’t caught up.

Pattern 4: Hand Claude a reference doc when it matters

When: a reference doc matters at one moment and not for the rest of the session.

A PostToolUse hook runs after a tool call succeeds and can return additionalContext. Claude Code wraps that string in a system reminder, a note placed next to the tool result, and Claude reads it on its next request. A deployment checklist that arrives right after kubectl apply is in front of Claude while it reads the apply output, instead of sitting in CLAUDE.md all session.

A small manifest maps tool calls to docs:

{
  "push_triggers": [
    { "trigger": { "tool": "Bash", "command_pattern": "\\bkubectl\\s+apply\\b" },
      "resource": "deployment-checklist" },
    { "trigger": { "tool": "Bash", "command_pattern": "\\bhelm\\s+upgrade\\b" },
      "resource": "deployment-checklist" }
  ]
}

The hook checks each trigger against the call and sends a doc the first time it matches in a session, keyed on session_id like Pattern 3:

#!/usr/bin/env python3
"""PostToolUse hook: send a reference doc the first time its trigger matches in a session."""
import json
import os
import re
import sys

HERE = os.path.dirname(os.path.abspath(__file__))
STATE = os.path.expanduser("~/.claude/hooks/state/injected")

event = json.load(sys.stdin)
args = event.get("tool_input") or {}
with open(os.path.join(HERE, "triggers.json")) as f:
    rules = json.load(f)["push_triggers"]

for rule in rules:
    t = rule["trigger"]
    if t["tool"] != event.get("tool_name"):
        continue
    # A missing pattern is "" and matches anything.
    if not re.search(t.get("command_pattern", ""), args.get("command", "")):
        continue
    if not re.search(t.get("file_path_pattern", ""), args.get("file_path", "")):
        continue
    marker = os.path.join(STATE, event.get("session_id", "unknown"), rule["resource"])
    if os.path.exists(marker):
        continue  # already sent in this session
    os.makedirs(os.path.dirname(marker), exist_ok=True)
    open(marker, "w").close()
    with open(os.path.join(HERE, "resources", rule["resource"] + ".md")) as f:
        doc = f.read()
    json.dump({"hookSpecificOutput": {"hookEventName": "PostToolUse",
                                      "additionalContext": doc}}, sys.stdout)
    break

Check the built-in options before writing one. Path-scoped rules are markdown files in .claude/rules/ with a paths list in their frontmatter, and Claude Code loads one when Claude reads a matching file. Most of a CSS style guide belongs in a rule with paths: ["**/*.css"], which loads when Claude reads a stylesheet. Skills load their instructions when they’re invoked or when Claude judges them relevant. A hook earns its place when the trigger is a command, like kubectl apply, rather than a file.

How it fails: compaction and size

Compaction undoes the injection. When Claude Code compacts a long conversation, context that hooks added is summarized with everything else, but the marker recording that a doc was sent survives. The doc never comes back. A SessionStart hook with the compact matcher clears the session’s markers so each doc can fire again:

#!/bin/bash
# SessionStart hook, matcher "compact": compaction summarizes injected docs away,
# so forget which ones this session was sent and let them fire again.
session=$(jq -r '.session_id // empty')
[ -n "$session" ] && rm -rf "$HOME/.claude/hooks/state/injected/$session"
exit 0

Size is the other limit. Each additionalContext value is capped at 10,000 characters. Past that, Claude gets a file path and a 2,000-character preview, and nothing tells it to read the file. The docs also recommend writing injected text as statements of fact rather than commands, because text that reads like a system instruction can trigger Claude’s prompt-injection defenses. The deployment notes in the companion repository are written that way: “Image tags are pinned to a version.”

How the four fit together

The patterns share the two tool events. The orchestrator runs the PreToolUse checks, session state decides which warnings still fire, and the injector runs after the tool:

Pattern Hook event Purpose Fires
PreToolUse interception PreToolUse Block or redirect a tool call Before the tool runs
Orchestrator PreToolUse Run several checks in a fixed order Before the tool runs
Session state Any Warn once per session, keyed on session_id First match in a session
Context injection PostToolUse Send a doc when it becomes relevant After the tool runs

Registered together, the whole setup is three entries in settings.json:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.claude/hooks/pre-bash-orchestrator.sh"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 $HOME/.claude/hooks/post-tool-injector.py"
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "matcher": "compact",
        "hooks": [
          {
            "type": "command",
            "command": "$HOME/.claude/hooks/reset-injected.sh"
          }
        ]
      }
    ]
  }
}

Where I’d start

  1. Keep guidance in CLAUDE.md. When a rule has to hold every time, move it into a PreToolUse hook with an if condition.
  2. Pipe test JSON through each check, including commands it should allow.
  3. At the third check, switch to an orchestrator and list blocks before rewrites.
  4. Key per-session state on session_id.
  5. Before writing an injector, try a path-scoped rule or a skill.

Every failure in this post was a hook doing exactly what I wrote, on every call, without an error. That consistency is what I moved the rules out of CLAUDE.md to get, and it means a wrong pattern stays wrong until a test catches it.
